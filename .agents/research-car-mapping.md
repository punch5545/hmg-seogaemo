# Car mapping: NEEV.KOR.260902

## Verified findings

**How the report mapped an unknown car.** The 2026-11-02 pre-install report says `map.status=none`, `hooks_on=false`, but its separate `map_car` probe found 324 points, 12 `by_reference`, and missed only `themesettings.split_item.type` (`tmp/car-reports/car-report-neev-kor-260902-20261102-2115.json:109-133`). The report code invokes `MapProbe` on the car's `/system` plus HMG-API stock backups and records its names and MD5s; it does this even without an active map (`tmp/HMG-API/core/runtime/java/hmgapi/engine/Report.java:63-91`). Thus the report demonstrates *discovery*, not that HMG-API hooks were enabled at report time. The owner's later working hotspot/CarPlay test is a separate observation; this report does not record the subsequent map installation or verification step.

**Algorithm.** `core/hookpoints/*.json` defines stable IDs, app package, stock files, and each point's `kind`, owning class (`of`), and `find` shape. Shapes include package/exact class name, superclass, constructor signatures, field/method names and types, static flags, parameter/return types, and code string constants. Named regex patterns can capture an obfuscated name from smali call patterns; `@point` references depend on an earlier class resolution (`tmp/HMG-API/core/hookpoints/README.md:1-36`; `tmp/HMG-API/core/hookpoints/dipo.json:1-21`). The host `tools/map-car.py` uses baksmali on a pulled stock tree, including regex and `only_caller` checks; zero or multiple candidates leave a point missing, or fail `--strict` (`tmp/HMG-API/tools/map-car.py:1-22,205-262`).

On the unit, Java `MapProbe` parses dex embedded in `.odex`/`.jar` directly; this is **not Dalvik reflection** and does not run baksmali. It scans framework boot-classpath odex and each catalogue app/library, resolves dependencies, then requires one class/member matching the shape (`tmp/HMG-API/core/runtime/java/hmgapi/engine/Dex.java:16-23,45-68`; `MapProbe.java:12-27,59-74,97-159,186-287`). It cannot evaluate smali-only regex/`code` rules. For those, `by_reference` means it tries names from *other cars' maps*, retaining a candidate only when present on this car with the remaining shape; zero or multiple names fail (`MapProbe.java:19-22,76-95,237-313`). This is a real reference-name fallback, not the whole mapping algorithm. `engine map-car` stores a probe report; `--write` creates a `probed` map, which still needs `verify-map` before hooks run (`MapProbe.java:328-390`; `CarMap.java:18-32,127-139`). `verify-map` uses on-car `PathClassLoader`/reflection against stock APKs, libraries and framework to check exact classes, members, signatures and static flags without launching the apps, recording `map-check.json` (`MapCheck.java:13-19,35-94,101-119`). `probe-test.py` compares on-car mapper output with the host mapper on available stock trees; `test-hooks.py` checks each point across stock trees and `maps/coverage.json` (`tmp/HMG-API/tools/probe-test.py:1-7,37-75`; `tools/test-hooks.py:1-18`).

**Name comparison.** I compared all entries under the report's `map_car.points` with every non-`car.json` file in the sole checked-in car map, `tmp/HMG-API/maps/kia/ev6/usa/260507/`: **324/324 full entries identical, 0 different, 0 absent**. The US map has one extra point, `themesettings.split_item.type`, which the KOR probe could not resolve. Thus identical obfuscated names certainly contributed, including the 12 fallback points, while the other 312 were independently resolved from shapes. Despite identical entries, only **1/18** stock-file MD5s matches the US map; all four files required by Seogaemo differ (`report:136-156`; `tmp/HMG-API/maps/kia/ev6/usa/260507/car.json:12-31`). Equality of names does not prove binary compatibility or a working hook runtime.

**Time.** The upstream Car Report UI estimates “about a minute” and permits 600 seconds for report generation; no measured KOR mapping duration is in the report (`tmp/HMG-API/core/app/java/hmgapi/app/ReportTab.java:60-75`). Host mapping uses hundreds of MB of temporary smali and is unsuitable for the head unit (`tmp/HMG-API/tools/map-car.py:331-332`). Telechips timing and memory must be measured on the car.

**Seogaemo today.** `payload/data/car-map.json` is this report's fixed 324-point map. Root precheck requires the exact `NEEV.KOR.0000.V039.001.260902`, `neev_kr`, Android 4.4.2 and four odex MD5s before applying (`modules/wireless-carplay-and-aa/root/wireless-carplay-and-aa.sh:7-44`). It installs the map at `/system/etc/seogaemo/wireless-carplay-and-aa/car-map.json` (`:64-67`). Zygote checks the exact product and those four hashes again, then loads only that map (`payload/src/hmgapi/hook/HmgApi.java.src:21-41`; `Points.java.src:31-55`). A changed product or any of these four odex files disables application/hooks even if names remain equal. A change only in another mapped library can evade this four-file gate; affected points or native byte recipes may then fail at use time. No runtime remapping or on-car `verify-map` is present. The native recipes have their own byte checks (`.agents/wireless-carplay-and-aa.md:15-29`).

## Proposed Seogaemo design (inference; not implemented)

1. **Select and validate.** At package start, cheaply compare product and module-relevant stock-file MD5s with a bundled, known-good map set. Recheck before module enable and after firmware change. Bind a selected map to the full relevant hash set, catalogue version, and product; never treat equal names across different hashes as verified. If hashes are unknown, show “mapping needed” and keep hooks off. The zygote should read only an atomically published, validated map, with a final hash/product gate.
2. **Map on demand.** A confirmed `map this car` action runs a fixed root verb on a background worker, outside zygote and the app UI process. Port the small Java dex reader/mapper into a dedicated API-19/Java-7 tool launched via `app_process` or `dalvikvm` using the device's own framework jars; benchmark both launch paths. Read only the installed stock odex/dex and declared libraries for **wireless-carplay-and-aa**. Parse in bounded batches with progress, timeout, low-memory handling and cancellation. Never put a whole-system scan in startup or the tap handler. Reuse HMG-API's definitions for this AGPL-adapted module, retaining attribution; copying its Java mapper into shared runtime would extend AGPL obligations there and needs a licensing decision (`modules/wireless-carplay-and-aa/payload/NOTICE.md:3-15`). No installed HMG-API is assumed.
3. **Required points and acceptance.** Generate a manifest from this module's declared hooks and source uses: boot `framework.activity_thread`/`app_bind_data`; DiPO/iAP2/Bluetooth and CarPlay bridge; GPM/Android Auto; navigation cluster plus turn-list/value helpers; `btsettings` helper and `framework.context_impl`. Include every owner-class and `@point` dependency, including dynamic `Cluster` method IDs. Do not require unrelated launcher, panel, theme or vehicle points. Every required point must have exactly one candidate and pass on-car classloader/reflection verification before activation. A zero/multiple match or unverified reference fallback keeps the **whole projection hook set** off; report the point and reason. Keep native-recipe checks independent.
4. **Persist and share.** Write a names-only, versioned map plus product, exact file MD5s, app-file list, required/optional point results, missing reasons, `by_reference`, verification result and elapsed time to `/data/nemesis/backup/hmg-seogaemo/car-maps/` through a new package API operation with atomic publish and ledger record. Expose it in existing USB/ADB export as a redacted Car Report so the owner can review and promote a proven map into the bundled set. Do not include raw dex, personal identifiers or arbitrary paths. Make uninstall/revert ownership and cleanup explicit in the runtime contract first (`.agents/module-runtime-contract.md`, “Change ledger” and “Export”).
5. **UI and validation.** Settings → wireless module page shows current product/hash, bundled/verified/generated/failed mapping state, point count and failing IDs. “Map this car” uses shared `ui.ConfirmDialog` (Cancel default), then progress and result, without blocking navigation. Host tests use the owner's report as an exact expected-output fixture and synthetic dex fixtures for unique, missing, ambiguous and reference-only cases; full stock-tree parity tests run only when private stock trees are available. On-car phases: read-only timing/memory probe with ADB recovery; generate and export a map without enabling hooks; verify; enable one module with boot/revert checks; only then add the known-good bundle. No physical-car success is implied by host fixtures.

**Owner decisions:** permit AGPL-adapted mapper code within this module or resolve whole-runtime licensing; choose automatic background mapping on unknown firmware versus explicit only (recommend explicit after a cheap startup status check); decide whether a map generated on the car can activate immediately after verification or requires owner review/promotion (recommend on-car verification plus explicit module enable); set a time/memory budget from a parked-car measurement; decide retention of generated maps and redacted report fields.
