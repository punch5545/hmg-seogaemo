# Wi-Fi client on NEEV.KOR.260902

The former HMG-API descriptor/core design is superseded by the `wifi-client` module in `.agents/module-architecture.md`. The target installation is NEMESIS + HMG-Seogaemo only; HMG-API is not installed.

Research and design only, 2026-11-03. Source paths are relative to `tmp/`. The provided Car Report is cited as `car-reports/...json`; it predates installation of HMG-API's wireless mod. No STA test or simultaneous STA/AP test was performed here. The owner reported that a prior HMG-API installation exposed the stock **hotspot/AP** menu and wireless CarPlay after reboot, but no Wi-Fi **client/STA** menu. That installation is historical evidence, not a target dependency. Our own future `wireless-carplay-and-aa` module must supply the AP side.

## Verified facts

**Report and timing.** The report identifies an Ioniq 5, `NEEV.KOR.0000.V039.001.260902`, Android 4.4.2, `neev_kr`; it records `wifi_chip:false`, 90 features including `com.hkmc.software.wifi.module` and wired CarPlay, no `android.hardware.wifi`, `mods:[]`, no errors, 324 discovered car-map points, but no active hook map. Only cellular interfaces are present; neither `wlan0` nor `p2p0` is listed. Its network snapshot has `load_iptrules`, zero HMG-API network rules and no logged drops (`car-reports/car-report-neev-kor-260902-20261102-2115.json:5-16,64-96,110-118,2196-2236`). Thus it describes the **pre-install state**, not the now working AP. HMG-API tests SDIO device enumeration or a remembered marker, not radio functionality; a boot-timing/SDIO false negative is plausible. The false value cannot mean this physical unit lacks usable Wi-Fi, given the owner's later successful wireless CarPlay (`HMG-API/core/runtime/java/hmgapi/engine/SystemCheck.java:137-152`). A fresh report after the mod and reboot is needed to establish the active flags, interfaces and mod ownership.

**Upstream STA enablement.** HMG-API's generic mod request `"wifi":{"client":true}` adds `/system/etc/permissions/android.hardware.wifi.xml`, comments its removal line in `/system/onebin/{onebin}/featurexml.cfg`, and sets `persist.wifi.state=3`. Feature XML advertises Wi-Fi to PackageManager/Settings; commenting the removal line keeps it present after boot; the property selects Hyundai's client-plus-wireless start mode (`HMG-API/core/runtime/java/hmgapi/engine/Engine.java:444-504`; `HMG-API/docs/mod-reference.md:278-284`). The bundled `wireless-carplay-aa` does **not** request client mode: it adds wireless projection feature files, comments the hotspot removal line, sets projection/bridge properties and optional native/hooks/audio changes; its test explicitly expects no client feature (`HMG-API/mods/wireless-carplay-aa/mod.json:36-55,68-125`; `.../patches.json:11-45`; `.../test.sh:47-57`). Its checked-in compatibility list/maps name USA/CAN, not KOR, so verify the actual installed update rather than assuming this checkout is identical (`.../mod.json:11-35`; `.../patches.json:2-10`). The **AP** menu's appearance is consistent with restoring the hotspot feature after reboot; the exact Settings visibility rule is unproved. The absent **client** menu matches the mod's missing `android.hardware.wifi` request and `persist.wifi.state=3`. Confirm current permission files and PackageManager features on the car.

Leafia's optional `LEAFIA-WIFI-CLIENT` marker (commit `b29aa3fec7e5bda669c41f10a6d443babdf3868b`, first tag v1.0.3) writes `persist.wifi.state=3` to build.prop and the live property and adds `android.hardware.wifi.xml`; its projection package otherwise targets hotspot only. It snapshots/restores those files/properties and reboots after install (`HMG-Leafia-Plus/packages/wireless-carplay-aa/comp/1_projection/scripts/common.sh:447-459,541-546,567-615`; `.../README.md:29-31,40-50`). NEMESIS `wireless.projection` goes further: build.prop/live `persist.wifi.state=3`, `settings global wifi_on=1`, client/AA/CarPlay XMLs, commented wireless removal lines, `wpa_supplicant.conf` `p2p_disabled=0`, and removal of overlay `p2p_no_go_freq`; uninstall restores its snapshots (`hmg_nemesis/Sources/packages/wireless-projection/scripts/common.sh:394-469,519-585`). `wifi_on` requests active STA; the supplicant edits concern P2P and are not necessarily required for ordinary STA. A working client also needs the supplicant service/configuration and STA-capable driver firmware/NVRAM, none proven by feature flags. A reboot is required to validate feature-file changes and boot property behavior; a live property alone may not reload PackageManager or restart WifiService (`HMG-Leafia-Plus/packages/wireless-carplay-aa/comp/1_projection/scripts/post.sh:5-17`).

**AP concurrency.** Leafia calls one-radio client plus hotspot untested (`HMG-Leafia-Plus/README.md:50`). HMG-API's CarPlay bridge calls the head unit's `WifiManager` AP APIs, including `setWifiApEnabledForConnectivity`, rather than an independent hostapd controller (`HMG-API/mods/wireless-carplay-aa/src/hmgapi/mods/wireless/dipo/Bridge.java:438-462`). In the nearby AOSP Wi-Fi controller, enabling STA while AP is enabled calls `setHostApRunning(..., false)` before STA starts; a running AP rejects supplicant start ([AOSP WifiController](https://android.googlesource.com/platform/frameworks/opt/net/wifi/+/478dd44/service/java/com/android/server/wifi/WifiController.java), [AOSP WifiStateMachine](https://android.googlesource.com/platform/frameworks/opt/net/wifi/+/dba342b115f9b2fedf6a42afd4586f17c1eddbe7/service/java/com/android/server/wifi/WifiStateMachine.java)). Hyundai's vendor mode 3 may differ; simultaneous operation is **unverified**. Enabling STA could stop the CarPlay AP. Keep client off by default and use the module mutual exclusion with UI confirmation, disabling `wireless-carplay-and-aa` and its dependents before enabling client. Record AP state, `wlan0`/`p2p0`, driver interface combinations, channel, and Wi-Fi logs before/after a STA toggle. The pre-install report's absent interfaces provide no concurrency evidence.

**Ownership and firewall.** HMG-API rebuilds shared feature files/config from stock and restores properties when its mods release them (`HMG-API/core/runtime/java/hmgapi/engine/Engine.java:446-504,1691-1725`). Its wireless mod owns the wireless projection XMLs, hotspot removal-line change in the same `featurexml.cfg`, and `persist.ium.support`; bridge parts own `persist.sys.iap2.wifi` and `persist.iap2.iden.wireless` (`HMG-API/mods/wireless-carplay-aa/mod.json:53-55`; `.../patches.json:11-45`). It does **not** request `android.hardware.wifi` or `persist.wifi.state`. Although the client property is separate, its feature/config edits share files with HMG-API. Independent edits can be lost on HMG-API apply/restore. Leafia and NEMESIS also own these paths when installed.

The old report's IPv4/IPv6 filter policies are `INPUT ACCEPT` and `OUTPUT ACCEPT`; `fw_wlan_INPUT` and `oem_out` are empty, with no `wlan0` route or drop evidence. On that snapshot, ordinary outbound STA traffic, DHCP and DNS would not need new allow rules, but no connected-STA packet test exists. If post-install rules differ, trace counters/drops and add only the demonstrated port/interface rule. HMG-API's `network` declaration can insert validated rules into its own chains before stock chains; its `hmgapi net` keeper reapplies them after firewall or Wi-Fi restarts and removes them on disable (`car-reports/...json:2199-2236`; `HMG-API/docs/mod-reference.md:221-275`). The wireless mod declares no network rules (`HMG-API/mods/wireless-carplay-aa/mod.json:1-125`).

## Seogaemo `wifi-client` module design

The first version independently manages only `/system/etc/permissions/android.hardware.wifi.xml` and the Wi-Fi feature removal line in `/system/onebin/neev_kr/featurexml.cfg`. It is off by default. Require exact `NEEV.KOR.260902`, a detected physical Wi-Fi chip, validated stock file contents, and no HMG-API, Leafia, or NEMESIS package leftovers claiming either file. Snapshot existence, exact bytes, mode, and owner before changes; preserve snapshots through reapply and update. Restore the exact baseline on disable or uninstall and verify before deleting backups. After apply, require a head-unit reboot and check whether the stock Settings Wi-Fi menu appears. Network selection uses that stock menu; no Seogaemo picker is planned. `wireless-adb` depends on this module. It and `wireless-carplay-and-aa` are mutually exclusive: enabling either prompts with the modules that will be disabled, including dependents. Follow `.agents/module-architecture.md` for the state and root protocol.

`persist.wifi.state=3` will be tested later.

## On-car diagnosis and reversible test

On the target NEMESIS + HMG-Seogaemo setup, save a fresh baseline and run read-only checks over ADB first (use full-root NEMESIS daemon if needed):

```sh
getprop ro.build.product; getprop ro.mobis.targetdir; getprop persist.wifi.state
settings get global wifi_on
ls -l /system/etc/permissions/*wifi* /system/onebin/neev_kr/featurexml.cfg
grep -i wifi /system/onebin/neev_kr/featurexml.cfg
ls -l /data/misc/wifi; ps | grep supplicant; ps | grep hostapd; ps | grep dhcp
ifconfig; netcfg; ip route; ip link
iptables -S; ip6tables -S
logcat -d -s WifiStateMachine WifiService WifiController wpa_supplicant WifiHW
```

Capture `dumpsys wifi`, `pm list features`, Wi-Fi chip evidence, exact file bytes/existence/mode/owner, `wpa_supplicant` and overlay config, AP/CarPlay state, and DHCP baseline. Some toolbox builds lack `ip` or `dumpsys wifi`; fall back to `netcfg`/available `dumpsys`, and never assume `tail` exists. First check that no leftover HMG-API/Leafia/NEMESIS wireless owner claims the files. Enable `wifi-client`, inspect the planned file diff and saved baseline, then reboot fully. Verify `android.hardware.wifi` is advertised and the stock client menu/toggle appears. Use the stock menu to test scanning, authentication, DHCP/DNS, and connection. Record logs, interfaces, routes, and firewall counters at any failure. Verify the UI confirmation lists `wireless-carplay-and-aa` and its dependents when switching to client, and `wifi-client` plus `wireless-adb` when switching back. Repeat apply and reboot, disable, update, and uninstall; compare exact restored files and absence, then verify menu/AP/CarPlay behavior. Retain backups on any restore failure. The exact post-enable STA behavior remains unknown.
