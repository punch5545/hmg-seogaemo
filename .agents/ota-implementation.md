# OTA implementation notes (2026-11-03)

- The signed manifest is a deterministic compact JSON object. `UpdateVerifier` deliberately accepts only the schema-1 byte format emitted by `tools/package.py`, so a changed serializer/schema requires an updater change. It checks the RSA signature with the embedded `keys/ota-manifest-public.pem` key, target, monotonically greater dotted version, exact four asset names, and OTA zip size/hash before extraction. It rejects duplicate or unsafe ZIP names and bounds compressed and expanded bytes.
- The app permits only HTTPS `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, and `objects.githubusercontent.com`, forces TLS 1.2, retains hostname checks, and accepts the transport certificate chain without consulting the Android 4.4 trust store. Release authenticity rests solely on the signed manifest. This must be validated against GitHub redirect behavior and the head unit's TLS/SNI implementation on-car.
- The fixed `core/update.sh` calls the **installed old APK** with `app_process` for root-side signature/hash checking and ZIP extraction. This avoids depending on `openssl` or `sha256sum` in KitKat toolbox. It never runs a verifier from the downloaded payload. The old APK's public key is part of the release trust root; key rotation needs an explicit compatibility plan.
- Root state lives under `/data/nemesis/backup/seogaemo/update`. A symlink selects the current payload. The initial previous build is the stable NEMESIS package tree. The updater uses the shared root lock directory, journals phases, keeps the previous build, and changes the installed descriptor's `package-version` only after APK install and basic health checks. Java `File.renameTo()` replaces the symlink atomically; shell `mv` followed directory symlinks in host tests and was rejected. The fixed boot reconcile wrapper rolls back a transaction interrupted in `applying`, `auto-rollback`, or `rollback`, then dispatches to the selected payload's reconcile script.
- The app persists the pre-transition enabled module IDs and `update-check` resume intent in private preferences. After update, cancellation, or failure it requests the previous module set through `ModuleManager`; it retains the snapshot if restoration fails. Actual status and transitions depend on the module runtime implementation.
- `app_process` launch, `dumpsys package` version output, root filesystem atomic rename/durability, module reconciliation, and APK signer continuity still need physical-car testing. The current module reconcile script is a stub, so the OTA health check cannot yet prove module health. Directory fsync is not available through the chosen API 19 implementation and power-loss durability needs car validation.
