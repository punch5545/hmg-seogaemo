# OTA implementation notes (2026-11-03)

- The signed manifest is a deterministic compact JSON object. `UpdateVerifier` deliberately accepts only the schema-1 byte format emitted by `tools/package.py`, so a changed serializer/schema requires an updater change. It checks the RSA signature with the embedded `keys/ota-manifest-public.pem` key, target, monotonically greater dotted version, exact four asset names, and OTA zip size/hash before extraction. It rejects duplicate or unsafe ZIP names and bounds compressed and expanded bytes.
- The app permits only HTTPS `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, and `objects.githubusercontent.com`, forces TLS 1.2, and uses the Android trust store and hostname checks. Release authenticity also requires the signed manifest. GitHub's certificate chain, redirects, and the head unit's TLS/SNI implementation must be validated on-car; Android 4.4 may lack a current root CA, in which case updates fail closed until a reviewed trust bundle is added.
- The app extracts the authenticated OTA ZIP into private `files/update/payload` and writes a per-file MD5 list. The fixed `core/update.sh` checks that list with toolbox `md5`, calls the **installed old APK** through `app_process` to copy and independently verify the signed manifest/OTA SHA-256, extracts the authenticated ZIP into a root-owned versioned directory with the trusted old APK, and checks the new directory's Java-generated MD5 list before activation. This avoids assuming `openssl`, `sha256sum`, `unzip`, `sed`, or `wc` on KitKat. It never runs a verifier from the downloaded payload. The old APK's public key is part of the release trust root; key rotation needs an explicit compatibility plan. Android 4.4.2 toolbox `md5` prints `<hex> <path>` ([AOSP source](https://android.googlesource.com/platform/system/core.git/+/android-4.4.2_r1/toolbox/md5.c)). MD5 is a change detector here; release authentication comes from RSA/SHA-256.
- Root state lives under `/data/nemesis/backup/hmg-seogaemo/update`. A symlink selects the current payload. The initial previous build is the stable NEMESIS package tree. The updater uses the shared root lock directory, journals phases, keeps the previous build, and changes the installed descriptor's `package-version` only after APK install and basic health checks. Java `File.renameTo()` replaces the symlink atomically; shell `mv` followed directory symlinks in host tests and was rejected. The fixed boot reconcile wrapper rolls back a transaction interrupted in `applying`, `auto-rollback`, or `rollback`, then dispatches to the selected payload's reconcile script.
- The app persists the pre-transition enabled module IDs and `update-check` resume intent in private preferences. It enables Wi-Fi client through the runtime's context-backed `ModuleManager.requestEnable`. After update, cancellation, or failure it requests the previous module set through `ModuleManager`; it retains the snapshot if restoration fails. Actual status and transitions depend on the module runtime implementation.
- `app_process` launch, `dumpsys package` version output, root filesystem atomic rename/durability, module reconciliation, and APK signer continuity still need physical-car testing. The integrated module reconcile script now performs desired-state application and reversion; OTA health still needs on-car proof. Directory fsync is not available through the chosen API 19 implementation and power-loss durability needs car validation.
