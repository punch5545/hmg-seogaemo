# Release-driven OTA update design

Research/design only, 2026-11-03. Paths are repository-relative. Target: NEMESIS 1.16.4+ and HMG-Seogaemo on Android 4.4.2; HMG-API is absent. No head-unit TLS or update test was performed. “Direct OTA” below still uses NEMESIS's root command channel for privilege; it bypasses its *package installer*.

## Verified facts

- At the time of this research, the APK hardcoded `versionCode=1`, `versionName=0.1.0`, and module descriptors each said `0.1.0`. The implementation now renders these from `VERSION` and supports a release keystore.
- NEMESIS `packages.db` stores ID, name, lock flag and types, **not** version. Installed version is parsed from `/data/nemesis/apps/<id>/NEMESIS.data`; `pkg-list` and `pkg-info` report that version (`tmp/hmg_nemesis/Sources/native/pkg.c:18-47,287-307,928-952,1010-1027`). Manager compares it with Store/USB catalog versions (`tmp/hmg_nemesis/Sources/manager/src/com/nemesis/manager/PkgUpdates.java:28-40,65-75`). Its own NEMESIS updater is separate (`UpdateService.java:49-85`). A direct update that leaves the descriptor old makes My Packages and package-update checks stale. The Store also requires a separately submitted package; a GitHub Release alone does not populate it (`tmp/hmg_nemesis/07-Submit-a-Package.md:11-56`).
- `nemesis install --update <zip>` exists (`tmp/hmg_nemesis/Sources/native/main.c:5`; `Sources/native/pkg.c:759-776`). It stops services, runs the **old** preuninstall, removes the old tree, and installs the new one; failure after removal can leave no installed package (`pkg.c:851-889`). That is explicitly an update *through NEMESIS*. The existing design's staged-update hook preserves module state (`.agents/module-architecture.md`, “State, privilege, and recovery”). Its shell app entry avoids NEMESIS's automatic APK uninstall (`.agents/research-nemesis-packaging.md`, “APK installation”).
- Root `pm install -r` needs the temporary `sys.boot_completed=0` workaround; restore the original property even on failure and check `pm` output plus `pm path`. Keep the same APK signer to retain app data; a signer mismatch requires uninstall and loses data (`tmp/hmg_nemesis/Sources/native/pkg.c:460-549`). The unit may lack `tail` and working toolbox remount (`tmp/HMG-API/CLAUDE.md:52,58`).
- GitHub's [latest-release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) returns the newest non-draft, non-prerelease by release `created_at`, not necessarily the highest version. Public reads need no token. [Asset API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset) allows `200` or `302`; `browser_download_url` may redirect. GitHub documents `release-assets.githubusercontent.com` for [release downloads](https://docs.github.com/en/actions/reference/runners/larger-runners). Unauthenticated REST API limit is [60 requests/hour per IP](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
- Android's [SSLSocket table](https://developer.android.com/reference/javax/net/ssl/SSLSocket) says TLS 1.2 is supported from API 16 but enabled by default only from API 20. NEMESIS Manager uses `HttpsURLConnection`, a TLS 1.2 socket factory, hostname verification, and a bundled-root fallback (`tmp/hmg_nemesis/Sources/manager/src/com/nemesis/manager/Portal.java:151-161,237-319`). Its `res/raw/nemesis_roots.pem` includes ISRG, DigiCert, GlobalSign, Amazon, GTS and others; these are TLS trust anchors, not release-signing keys. [Let's Encrypt](https://letsencrypt.org/ta/docs/certificate-compatibility/) lists Android 7.1.1+ for native ISRG Root X1 trust, so stock 4.4 cannot be assumed to trust modern chains. Current issuer/chain for all four GitHub hosts was **not verified** here; certificates rotate. Measure `api.github.com`, `github.com`, `release-assets.githubusercontent.com`, and `objects.githubusercontent.com` on the car before selecting bundled roots. Do not pin a transient leaf or disable hostname checks. Preserve SNI by connecting with the DNS hostname, and allow only HTTPS redirects to vetted GitHub asset hosts. Check the head-unit clock before TLS.
- API 19 supports `SHA256withRSA` and `SHA256withECDSA`; Ed25519 is unavailable ([Android crypto support data](https://android.googlesource.com/platform/libcore/+/master/tools/docs/crypto/data/crypto_support.json), [Java 7 Signature](https://docs.oracle.com/javase/7/docs/api/java/security/Signature.html)). NEMESIS 1.16.4 calls its opt-in “Use built-in modem for network services” (`tmp/hmg_nemesis/README.md:82-85`), but the gate is in Manager's own `Portal.java:101-133`; it does not grant Seogaemo a network route. The route/modem behavior for our app remains untested. HMG-API's `updates` option affects the car's OEM OTAClient, not Seogaemo releases (`tmp/HMG-API/CLAUDE.md:68`).

## Proposed implementation (inference)

**Version and release contract.** Add numeric `VERSION` (`MAJOR.MINOR.PATCH`) as the only edited project version. Require tag `v$(cat VERSION)` and monotonic versions. Generate Android `versionName` and a checked 31-bit `versionCode` (for example `major*1000000 + minor*1000 + patch`, each minor/patch below 1000), NEMESIS `package-version`, every built-in module's version (replace the current literal module `version=` with a build-time placeholder), an APK BuildConfig-like constant, and root `/data/nemesis/backup/seogaemo/installed-version` from it. Keep `NEMESIS.data` descriptor `version=1.1` separate. `PackageManager` and root status must agree; refuse to claim success otherwise. Module versions can diverge later only through an explicit schema change. Current module graph remains generated from `modules/*`, never hand-maintained (`.agents/module-architecture.md`, “Source and package layout”).

**Authenticated release.** Publish a detached signed manifest and signature beside the zips. Sign the exact bytes of a deterministic UTF-8 manifest (or canonical JSON) containing version, target model/OS, schema version, asset names, sizes and SHA-256 hashes, including the OTA zip. Embed an RSA-3072/SHA256 verification public key in both old APK and immutable root updater; verify signature, then every byte/size, before execution or `pm install`. Match the tag, manifest version and expected asset name; reject duplicates, traversal, oversized files and unsupported models. Store a root-side highest accepted version to block remote rollback; an automatic rollback to the immediately previous verified build is the only internal exception. An **offline** manifest key, held by the owner and used after CI builds, gives strongest separation but prevents fully unattended release publication. For the requested automatic pipeline, put **separate** APK and manifest private keys in GitHub repository secrets, restrict signing to a protected release environment with approval, and accept that this makes the manifest key online ([GitHub environment protection](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). Never commit either private key or copy it to the device. A SHA-256 value supplied only by the GitHub API is insufficient against a compromised release account.

Put the Java fetcher/verifier in `app/src/com/seogaemo/app/core/update/`, the stable root updater in `nemesis/package/core/update.sh`, and route only the fixed update verbs through `nemesis/package/bin/seogaemo-root`; the generated module graph stays in the payload. This keeps release handling outside individual modules.

**Direct update transaction.** App Java fetches metadata/assets with bounded `HttpsURLConnection`, TLS 1.2 factory and bundled, reviewed CA roots; Java is preferable to assuming root-side `curl`/`wget` exists. Poll at boot and at most daily while connectivity is already present, then automatically download/apply a newer signed release; the button checks immediately. Download into a private, same-filesystem staging directory. Root command accepts only fixed verbs: `seogaemo-root update stage|apply|rollback|status`, never caller paths. Under one root lock, reverify signature/hashes, journal intent, copy a complete versioned payload (dispatcher, `modules/*.sh`, generated `modules.list`/`modules.graph`, reconcile script, APK), durably flush files/directories, then atomically rename a `current` symlink to the new payload. Preserve the previous payload and APK. Install the signed APK with the boot-property workaround; verify Android package version/signature, root status, module graph, and a boot reconcile health check. On failure or interrupted boot, the **old, fixed boot wrapper** switches the pointer back and reinstalls the previous APK; preserve module baselines and journal. Never treat a module reapply as a new baseline. Make state migrations backward compatible or block direct OTA. A process cannot safely replace the script currently executing it; the fixed wrapper must launch a separate, immutable updater/rollback helper.

Keep NEMESIS hook and service entry scripts as stable wrappers in `/data/nemesis/apps/seogaemo/`; they dispatch to the versioned payload only after health checks. Do not casually rewrite `preuninstall`/`postinstall` in place: a half-written restore hook can prevent safe uninstall. For a hook/descriptor schema change, use the signed NEMESIS package zip and `nemesis install --update` after a validated state-preserving preuninstall path; that changes the Manager record and service registration normally. For payload-only direct OTA, atomically replace **only the installed descriptor's `package-version` after health succeeds**, preserving all other fields, and check `nemesis pkg-info seogaemo`; `packages.db` needs no version edit. This is an intentional NEMESIS metadata mutation, so validate on-car that Manager reloads it and that a later NEMESIS uninstall uses the stable hook. If that metadata edit is unacceptable, use the CLI package path for every release.

**Connectivity and UI.** If STA is already connected, check directly. Otherwise, first try an observed existing non-STA route (USB/Bluetooth hotspot or permitted modem); Manager's modem preference is not proof our process can use it. If none works, Settings > General → About shows current version and “Check for updates”, explains that enabling `wifi-client` disables `wireless-carplay-and-aa` and requires a head-unit reboot, and requests a deliberate choice. Persist update intent plus prior desired module set on the root side; enable client, reboot, resume check after boot, then restore the prior set after success/failure. Restoring projection may need a **second** reboot and will disconnect Wi-Fi; do not claim completion before observed status. `wireless-adb` depends on client and must be included in the transition plan (`.agents/module-architecture.md`, “Module contract”; `.agents/research-wifi-client.md`, “Seogaemo wifi-client module design”). Offer signed USB zip fallback through `/storage/usb*/...` with the same signature check; normal NEMESIS USB install is another recovery route. UI shows check/download/verify/apply/reboot/rollback progress and exact failure reason in Logs, with a manual rollback action for the retained build.

**Release pipeline and test.** A tag-push workflow validates `VERSION`, runs `make test`/API-19 build, signs APK with release keystore, builds `seogaemo-<v>-nemesis-package.zip`, `seogaemo-<v>-nemesis-usb.zip`, and `seogaemo-<v>-ota.zip` (APK + root payload + graph), then creates `seogaemo-<v>-manifest.json` and `.sig` as sidecar assets. Upload all assets to a *draft* release, verify hashes/signature, then publish it so `/releases/latest` never points at a partial release. The device derives the exact expected names from the API tag, verifies the signed manifest, then checks zip hash, tag/version, monotonicity and target before applying. On a car, test TLS/redirect/CA/SNI and wrong clock; Wi-Fi transition with CarPlay active; success, signer mismatch, bad signature/hash, power loss at each journal phase, failed APK install/reconcile, automatic rollback, subsequent NEMESIS Store/USB update and uninstall, and restored module baselines. Keep an offline USB recovery image. Open owner decisions: offline manual signing versus automated CI signing; whether all releases should use the NEMESIS CLI for metadata simplicity; whether modem use is allowed; whether two reboots/CarPlay interruption are acceptable; retained rollback depth and free-space threshold.

## Owner decisions (2026-11-03)

- Telematics modem must **not** be used for updates. Only `wifi-client` (or USB stick fallback).
- CarPlay interruption and extra reboots during an update are accepted.
- Avoid NEMESIS as much as possible: APK, module scripts, root payload, module graph and CA bundle are updated by Seogaemo itself. NEMESIS hook/service entry scripts stay thin, stable wrappers that only dispatch into the versioned payload, so they should practically never change; `nemesis install --update` is a rare last resort for wrapper/descriptor schema changes.
- Open: transport/TLS approach (see chat proposal: signed manifest is the security boundary; TLS is transport only) and release signing key custody.
- Decided: signing keys live in GitHub. Environment `release` on seogaemo/hmg-seogaemo, deployments limited to tags `v*`.
  Secrets: `RELEASE_KEYSTORE_B64` (PKCS12, base64), `RELEASE_KEYSTORE_PASSWORD` (store = key password),
  `RELEASE_KEY_ALIAS` (`seogaemo`), `OTA_MANIFEST_PRIVATE_KEY_PEM` (RSA 3072, SHA256withRSA).
  Release APK cert SHA-256: `3A:71:C3:82:C9:75:98:E1:7F:BE:68:8E:9F:11:69:A9:57:50:03:74:9D:D6:B1:9C:E8:74:60:CC:5D:E1:E8:53`.
  Public manifest key for the app/root updater: `keys/ota-manifest-public.pem`. The release workflow must use `environment: release`.

## Current release implementation

The first release pipeline publishes the NEMESIS package zip, USB zip, APK,
`SHA256SUMS`, and a SHA256withRSA signed JSON manifest and detached signature.
All release asset names use the `hmg-seogaemo-<v>` prefix except `SHA256SUMS`.
The manifest lists the APK and two zips with byte sizes and SHA-256 hashes;
`SHA256SUMS` additionally covers the manifest and signature. This is release
packaging only: the proposed direct OTA client, root transaction, rollback,
and `ota.zip` do not yet exist. The release job uses the `release` environment,
checks the tag against `VERSION`, verifies the distribution and the expected
APK certificate, uploads to a draft, confirms all six asset names, then
publishes the release.
The About screen reads `PackageInfo.versionName` at runtime, avoiding a
second literal version in localized string resources.
