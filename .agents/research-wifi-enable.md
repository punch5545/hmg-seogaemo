# Wi-Fi enablement on NEEV.KOR.260902

Source review, 2026-11-03. Paths below are relative to `tmp/`; no car was tested. **“Wi-Fi off” has three meanings here:** the Wi-Fi chip/radio, Android Wi-Fi client and its Settings menu, and the hotspot used by wireless CarPlay/Android Auto (AA).

## Verified findings

**Identity and limits.** `NEEV.KOR.260902` parses as Hyundai Ioniq 5, Korea, firmware 260902 (`HMG-API/core/runtime/java/hmgapi/engine/SystemCheck.java:49-55,76-90`). Leafia added this car in commit `be8118e4708910037540edc09b64435514ffdfad` (in v1.0.0), but its current `patches/neev_kr/` is retained **outside** `patches/cars`; the README says no Korean unit checked so far has shown working Wi-Fi hardware (`HMG-Leafia-Plus/patches/README.md:9-15`; `HMG-Leafia-Plus/README.md:72-76`). A permission file saying `com.hkmc.software.wifi.module` does not prove a chip exists: Leafia checks `/sys/class/net/wlan*` or the DHD power-failure kernel message, and HMG-API checks SDIO devices or a previously recorded chip marker (`HMG-Leafia-Plus/packages/wireless-carplay-aa/scripts/common.sh:192-210`; `HMG-API/core/runtime/java/hmgapi/engine/SystemCheck.java:136-152`). Thus the claim that this *specific physical* unit has a chip merely switched off is **unverified**.

**Leafia release history.** The hotspot correction was added in `fc88c0770eb94ca44a3ca2ff4a6aa8d761c67883`, `packages/wireless-carplay-aa/comp/1_projection/scripts/common.sh` (included in tags v1.0.1 onward, including v1.0.2). It detects a stock active `-/system/etc/permissions/com.hkmc.software.wifihotspot.xml` line, comments it out, and adds missing hotspot and Android Wi-Fi feature XMLs. Current code retains that behavior (`.../comp/1_projection/scripts/common.sh:350-373,441-445,548-554`). Leafia v1.0.0 had already made its projection package “hotspot only”: it left `persist.wifi.state`, `settings global wifi_on`, `wpa_supplicant` and its overlay unchanged (tag `v1.0.0`: same path, lines 498-517). This removed the *client setup* inherited from NEMESIS's `wireless.projection`, which sets `persist.wifi.state=3`, `wifi_on=1`, the client feature XML and P2P config (`hmg_nemesis/Sources/packages/wireless-projection/scripts/common.sh:534-557`). Commit `b29aa3fec7e5bda669c41f10a6d443babdf3868b` (first in v1.0.3) added the `LEAFIA-WIFI-CLIENT` install-drive opt-in: it sets `persist.wifi.state=3` in `/system/build.prop` and live property and adds `android.hardware.wifi.xml` (`HMG-Leafia-Plus/packages/wireless-carplay-aa/comp/1_projection/scripts/common.sh:447-459,541-546`). The current README labels simultaneous client and hotspot operation on the one radio untested (`HMG-Leafia-Plus/README.md:29-31,50`). That opt-in is separate from the hotspot correction already present in v1.0.1–v1.0.2.

**Mechanism.** Leafia chooses the firmware's own `ro.mobis.targetdir/featurexml.cfg` when it contains wireless entries, otherwise searches feature files; it comments active wireless AA, CarPlay and hotspot removal lines, and adds the AA/CarPlay permissions files (`HMG-Leafia-Plus/packages/wireless-carplay-aa/comp/1_projection/scripts/common.sh:322-347,350-373,528-554`). It adds hotspot and Android Wi-Fi XMLs **only if the original hotspot removal line was active and those files were absent**. US firmware with the hotspot line already commented is left alone (`.../common.sh:441-445,548-554`). The correction is conditional on observed files, not hardcoded to KOR, NEEV or 260902. Leafia snapshots `/system/build.prop`, feature config, permission-file existence/content, properties and `wifi_on`; uninstall restores them and keeps snapshots on failure (`.../common.sh:466-512,567-615`). Its package postinstall reboots so PackageManager reloads features; the part script explicitly asks for a reboot (`.../scripts/post.sh:43-61`; `.../comp/1_projection/scripts/post.sh:5-17`). No reviewed correction loads a kernel module, edits `hostapd`, starts `wpa_supplicant`, or calls an init Wi-Fi service. A new feature XML may expose the Wi-Fi menu, but hotspot availability, radio power and menu visibility must each be measured on the car.

**HMG-API is different.** Its *core patch engine* implements a generic mod request `"wifi":{"client":true}` as `android.hardware.wifi.xml`, a commented removal line in `/system/onebin/{onebin}/featurexml.cfg`, and `persist.wifi.state=3` (`HMG-API/core/runtime/java/hmgapi/engine/Engine.java:444-504`; `HMG-API/docs/mod-reference.md:278-284`). The bundled `wireless-carplay-aa` mod does **not** request that client mode; its test asserts no client feature. Its projection part comments out the hotspot removal line, but its compatibility and patch-set map list only USA/CAN, not KOR (`HMG-API/mods/wireless-carplay-aa/mod.json:11-35,53-56`; `.../patches.json:2-19`; `.../test.sh:57`). Therefore HMG-API supplies a generic mechanism, **not an available NEEV.KOR.260902 fix as shipped**. HMG-API detects Wi-Fi hardware through SDIO, rather than trusting the permission feature alone (`HMG-API/core/runtime/java/hmgapi/engine/SystemCheck.java:37-38,136-152`).

**Interactions and ownership.** The hotspot is `wlan0` at `192.168.0.1/24`; the stock ADB switch can assign `eth0` `192.168.0.123`, disrupting hotspot DHCP. Our `wireless-adb` needs an actually running/reachable hotspot before advertising `192.168.0.1:5555` (`HMG-API/CLAUDE.md:56`; `.agents/research-adb-wireless-module.md`). Leafia's projection part and NEMESIS `wireless.projection` touch the same feature config and Wi-Fi feature XML; HMG-API's engine also owns these via feature flags. Do not independently rewrite them while another package owns them (`hmg_nemesis/Sources/packages/wireless-projection/scripts/common.sh:519-557`; `HMG-API/core/runtime/java/hmgapi/engine/Engine.java:446-504`). The hotspot correction alone does not guarantee working wireless CarPlay/AA, which also need projection flags, bridge and firmware-specific support (`HMG-Leafia-Plus/README.md:21-38`). Leafia's relevant package scripts derive from NEMESIS and remain AGPL-3.0; Leafia's original work is GPL-3.0, HMG-API is AGPL-3.0. Reimplement observed behavior independently (`HMG-Leafia-Plus/NOTICE.md:5-15`; `HMG-API/README.md:100`).

## Superseded Seogaemo core proposal (historical only)

Keep this **outside** `modules/`: `app/src/com/seogaemo/hmg/core/WifiEnableStatus.java` (state/UI adapter) and `nemesis/package/core/wifi-enable.sh` (root check/apply/restore/status). Extend `nemesis/package/bin/hmg-seogaemo-root` with fixed `wifi-enable status|apply|restore` verbs; no arbitrary paths or shell text. In Settings > General show “Wi-Fi hotspot support” with observed chip, stock feature, applied/pending-restart and conflict state; offer a “Restore stock Wi-Fi configuration” action/override, not a module toggle. This follows the root/state contract in `.agents/module-architecture.md` while keeping `wireless-adb` a separate module.

Gate mutation on a validated `NEEV.KOR.260902` hardware sample, working SDIO/`wlan*` evidence, exact stock feature-file pattern, and no Leafia/NEMESIS/HMG-API ownership. Until that sample exists, report unsupported and make no mutation. Once validated, package postinstall captures byte-exact file baselines (including absence, mode and owner) under `/data/nemesis/backup/hmg-seogaemo/core-wifi/`, comments only the active hotspot removal entry, creates only the missing required feature XMLs, then requests a head-unit reboot. A one-shot boot reconcile service verifies state and chip without repeated writes; a user override restores stock and suppresses reapply. Real NEMESIS uninstall restores the exact baselines before removal and fails closed if another owner has changed the files. `wireless-adb` reports “hotspot unavailable” until `wlan0`/address/reachability is observed; it must not silently activate Wi-Fi client mode. Avoid `persist.wifi.state=3` and `wifi_on=1` unless a separate client-mode requirement is agreed and tested.

## Owner decisions and car checks

Decide whether automatic hotspot correction should ship after validation or require a one-time user action, and whether Wi-Fi client mode is desired at all. On a real NEEV.KOR.260902, capture untouched `ro.build.product`, `ro.mobis.targetdir`, `featurexml.cfg`, all three feature XMLs, `persist.wifi.state`, `wifi_on`, SDIO/DHD logs and `wlan*`; establish whether a physical chip responds. Then test hotspot startup, `192.168.0.1`, DHCP, Settings menu, CarPlay/AA and wireless ADB before/after reboot and after exact uninstall restoration. If no chip responds, this software correction cannot make one appear.
